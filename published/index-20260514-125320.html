OP Snapshot Restore and Lateral State

A non-genesis snapshot exposed a gap between Feldera's durable collection checkpoint and the in-memory state used by OP execution lateral views. This document explains the problem, the pragmatic V1 solution, and the more principled Feldera-native alternative.

Recommendation Use product-side restore hydration as the supported V1 path. Treat Feldera-native lateral checkpointing as the long-term architectural target, but do not rely on it until it has dedicated DBSP tests that prove hot state, cache state, finalization state, cold-store state, and continued evaluation restore correctly.

Short Version

Feldera can checkpoint the persisted dataflow collections that power SQL queries. The OP executor also uses a lateral view named execute_l2_block. That lateral view reads previous execution state through a fast in-memory handle. After restore, SQL could still see block 1, but the lateral handle could not. When block 2 arrived, execution could not find block 1 as its parent and produced an empty result.

The pragmatic V1 fix is to reconstruct the executor lateral handle from the restored SQL state views during snapshot restore. The architecturally cleaner fix is for Feldera's lateral operator itself to participate fully in checkpoint and restore, so product code does not need to know how to rebuild lateral internals.

What Is a Lateral View?

Most SQL views are relational: rows flow in, rows flow out, and Feldera keeps the result incrementally up to date. A lateral view is different. It is a controlled escape hatch for stateful sequential work. In op-con-ex-node, the important example is L2 block execution.

To execute block N, the executor needs facts produced by earlier blocks: parent block metadata, account balances, storage slots, bytecode, and rollup config. SQL declares which state views the lateral evaluator can read. Rust runs the sequential execution logic.

The Snapshot Restore Problem

A product snapshot wraps a Feldera checkpoint plus ethql-owned metadata and external assets. Feldera's checkpoint restores persisted collections. That is necessary, but it does not automatically guarantee that every in-memory lateral state handle is ready to answer the next lateral evaluation.

The test that exposed the issue restored a snapshot at block 1, then sent block 2. Public SQL queries could see block 1. The executor lateral state could not see block 1. So block 2 execution treated its parent as missing.

Why this is easy to miss

  • SQL queries after restore look correct because the persisted collections are back.
  • The restored current head can be correct before any new execution happens.
  • The failure only appears when a later block asks the lateral evaluator to read prior state.

Preferred V1 Solution

During snapshot restore, after Feldera restores the persisted checkpoint and before the node serves normal traffic, op-con-ex-node should hydrate the executor lateral handle from the restored SQL state views.

In concrete terms, restore reads these state sources:

  • exec_evm_accounts
  • exec_evm_storage
  • exec_evm_code
  • exec_block_meta
  • the rollup config projection used by exec_rollup_config

It converts those rows back into execute_l2_block_StateRow variants and inserts them into the lateral handle at their original versions. After that, block 2 sees block 1 through the same lateral state interface it would have used without a restore.

The Alternative: Feldera-Native Lateral Restore

The "right" place to solve this in the long run is Feldera, not op-con-ex-node. A lateral evaluator is a DBSP operator with internal runtime state. If Feldera advertises checkpoint/restore for a circuit, every stateful operator in that circuit should restore to a state where the next input can be processed correctly.

In that design, GenericLateralEvalOp would be a first-class checkpoint participant. It would save and restore the state that is not represented by ordinary SQL output collections, and its external LateralStateHandle would be populated before normal execution resumes.

What Feldera would need to own

State Why it matters Long-term requirement
Hot lateral state The versioned rows read by the next lateral probe. Checkpoint or deterministically rebuild before the first post-restore step.
Cached probe outputs Used by the generic operator to retract or reuse prior evaluations. Restore, or define a safe replay protocol that recreates them before any retractions can arrive.
Access lists and reverse index Used to detect when a prior probe must be re-evaluated because state changed. Restore consistently with cached outputs, or invalidate and rebuild under a proven algorithm.
Finalization and cold store state Controls what is retained in memory and what is flushed to cold storage. Checkpoint hot/cold boundaries and ensure restored handles read both tiers correctly.

This is the cleaner abstraction boundary because it makes lateral restore a property of Feldera circuits rather than a special case in every product crate. It is also harder: the operator must preserve not only what a lateral state read returns today, but also enough internal bookkeeping to handle later retractions, invalidations, finalization, and cold-store reads.

Comparing the Two Approaches

Question Product-side hydration Feldera-native lateral checkpointing
Best fit V1 production path for op-con-ex-node snapshots. Long-term platform path for all lateral users.
Owner op-con-ex-node owns how execution state is reconstructed. Feldera owns lateral operator checkpoint and restore semantics.
Correctness surface Narrow: restore the exact state the OP executor reads next. Broad: hot state, cached outputs, access indexes, watermarks, finalization, and cold stores.
Product coupling High: it knows about execute_l2_block state rows. Low: product code asks Feldera to restore the circuit.
Test burden Integration tests around OP snapshot restore and continued execution. DBSP operator tests plus product integration tests for every lateral restore mode.
Failure mode Hydration can drift if SQL state shapes or executor state rows change. Generic restore can be subtly wrong under retractions or finalization if internal indexes are incomplete.
Operational story Explicit and auditable in the ethql snapshot manifest/restore flow. Simpler for operators once proven: Feldera checkpoint means full circuit checkpoint.

The right final architecture is Feldera-native. The right current implementation is product-side hydration, because it is smaller, explicit, testable today, and aligned with the V1 snapshot contract. We should avoid presenting product hydration as the ideal end state; it is a compatibility layer that lets the product ship safely while the platform-level restore contract matures.

Operational Contract

The V1 snapshot contract should say:

  • The Feldera checkpoint is the source of truth for restored SQL collections.
  • The ethql manifest is the operator-facing compatibility and integrity contract.
  • op-con-ex-node owns reconstruction of product-specific external and lateral execution state.
  • Restore must verify the boundary head and state root before normal service starts.
  • Restore must prove continued execution from the restored boundary in integration tests.

Recommended Follow-Up

If we want Feldera-native lateral checkpointing later, build it as a separate Feldera task with a small fixture lateral operator:

  • Create state, probes, cached outputs, and finalization activity.
  • Checkpoint and restore the DBSP circuit.
  • Verify external handle reads after restore.
  • Submit new probes and verify continued lateral evaluation.
  • Repeat with finalized state and cold-store movement.
Suggested owner: op-con-ex-node for V1 product restore, Feldera runtime for any later generic lateral checkpoint contract.
